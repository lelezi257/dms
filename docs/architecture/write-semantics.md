# 写语义

AFS 的写语义以 POSIX 风格可见性为目标，但把普通写、持久屏障和版本提交分开处理。

## 可见性

- 同一挂载内，读可以看到本地已接受但尚未提交的 dirty 写。
- 跨挂载和远端读按 close-to-open：前一个打开者完成必要 close/flush 后，后续 open 才应看到确认内容。
- 普通写成功不代表持久化成功。

## 持久屏障

`fsync`、`fdatasync`、同步写标志和 close-time barrier 会触发必要的持久化和提交。若底层存储或 Meta 提交返回不确定结果，系统必须保留请求身份并在恢复时判定，不能直接当作成功。

## 错误传播

一旦某个句柄遇到致命 sync 或存储错误，后续 write、truncate、flush、sync 和 close 必须继续返回该错误，直到句柄释放。读和 release 可以继续执行，但不能把之前未确认的写伪装成已持久。

## 当前验收

阶段一历史功能已关闭；当前版本的 OwnerFs 远端、bind ON、DFS 核心场景和性能验收见 [当前计划](../development/plan.md)。

## 未决提交与生命周期

提交结果不确定时，必须保留原请求身份、请求内容和恢复线索，并阻止对应 inode 的后续 write、resize 和 sync 越过未决提交。重试使用同一身份与同一请求；同身份不同内容必须拒绝，不能重放成另一笔写入。close/release 不能擦除未决身份或将未知结果报告为成功。

`flush` 必须允许重复调用并保持幂等；需要持久化的出口按文件与父目录屏障分别确认。`release` 只清理资源，不是持久化成功的证明。
