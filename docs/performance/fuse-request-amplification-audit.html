1. 这次把什么举一反三了

之前只知道“大请求分段数减少后会变快”。现在不再靠某个配置名判断，而是对每个用户操作建立统一账本：

POSIX 操作→FUSE callback→文件业务操作→DataCore→Meta / Peer

每层同时记录次数；read/write 和 DataCore 额外记录字节。验收器按 Case 冻结允许上限，后续无论 FUSE ABI、内核、actor 或缓存如何改，只要产生额外 callback、RPC、Block Pull 或整段复制就会失败。

3. 哪些看似放大，但现在不能局部删除

1 MiB 写 = 2 次 FUSE write + 2 次 commit。 当前内核把该写请求拆成两段；我们选择 write-through，所以每个 callback 发布成功后才能返回。 若强行只 commit 一次，就已经变成 writeback，需要新增脏页、flush/fsync、失败恢复和空间回收语义，不能伪装成局部性能优化。
TTL=0 与 DIRECT_IO 暂时保留。 Node 已通过 watch 撤销自己的 binding/cache，但尚未把失效事件闭环到内核 FUSE cache。 在具备 notifier 前启用较长 entry/attr/page cache 会改变跨客户端可见性，不是安全优化。
readdir 每页重新收集/排序是 P2，不在当前临时语义上扩建缓存。 当前目录只列出本 Node 已发现的 dentry，并非最终权威共享 namespace。应在 Meta 目录分页合同完成时一次解决分页、排序和缓存，当前增加第二套目录快照只会形成待删除状态。

4. max_pages 类问题的最终结论

fuser 0.16 + abi-7-31 已默认协商 ASYNC_READ、BIG_WRITES，并在内核支持时请求 MAX_PAGES；默认接收缓冲允许 16 MiB。当前不缺另一个手写的 max_pages 开关。

真正应长期保留的是“实测分段账本”：例如 1 MiB 热读是 3 次 FUSE read，但只有 2 次 DataCore read 且总字节恰好 1 MiB，因此第三次是 EOF 探测；如果未来变成 8 次 DataCore 或 8 次 commit，机器合同会直接失败。
