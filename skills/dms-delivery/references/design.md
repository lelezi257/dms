# 设计阶段模板

按下面顺序组织，图上的模块名、正文、API 和时序参与者使用同一名字。不能先扔出一张接口表再要求读者自行推导业务。

## 1. 用户输入与核心原理

用实际 key/value 和操作串起逻辑对象、版本、范围与物理内存；只解释本次涉及的概念。例如局部写必须展示修改前后 bytes、布局变化及旧数据的生命周期，而不是只说 overlay。

## 2. 部署图与一层模块

先画进程黑盒，再展开进程内一层核心模块；框表示归属，箭头表示调用方向。说明哪些是 unary、server stream 或 bidirectional stream，由谁发起。模块很多时按进程分图，不把一堆名字塞成无法阅读的图。

按图依次说明每个受影响模块的功能边界、核心状态和数据结构。状态 owner 是职责，不要无故再创造 Owner 模块。物理机制与业务语义分开。

## 3. 用户用例串流程

至少覆盖本次改变的主路径和关键差异路径，例如普通 SET、GET 命中/未命中、随机写。没有差异不强凑三个大图。每个用例先用业务语言串模块，再紧接时序图；异常和可靠性在读者理解主流程后解释。

## 4. 接口与状态就近放置

每类接口独立呈现：接口编号、提供者、调用者、核心函数原型（参数、返回值）及相邻状态结构。编号不能表示一整条不同服务链。时序图消息引用相同编号/函数，解释为什么需要多次交互与合并的边界。

说明可观察性、协议兼容、资源回收和性能预算中受本次影响的点；引用现有基础规则，不全量重写。设计草图不是已实现接口，明确标记。

## 5. 验证与 review

列出需要穿刺的未知、代码落点和测试形状。人工重点是边界、抽象必要性、关键用例是否能闭环；不要求本阶段确认所有函数体细节。
