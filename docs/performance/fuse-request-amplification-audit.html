Native Filesystem FUSE 请求放大审计

2026-09-17 · M1.7 discovery · 三台相同 Lima aarch64 VM · 当前分类性能门禁与独立 RPC 放大门禁

结论：当前 M1.7 discovery 门禁 PASS。 现行门禁已经拆成两类：性能分类门禁只判断各类场景是否达到合同，RPC 放大门禁只判断 FUSE/DataCore/Meta/Peer 次数和字节是否越界。1 MiB 写入当前是 1 次 FUSE write + 1 次 Meta commit；1 MiB 跨节点首读当前是 1 次 Meta lookup + 1 次 PullBlock。本文不是最终 clean release 结果。

1. 当前门禁检查什么

不再把“端到端时延”和“路径是否放大”混成一个历史 baseline。每个用户操作先生成统一账本：

POSIX 操作→FUSE callback→文件业务操作→DataCore→Meta / Peer

每层同时记录次数；read/write 和 DataCore 额外记录字节。RPC 放大验收器只看账本是否超过合同上限；性能验收器另行按 create、hot read、peer first read、overwrite 等类别判定，不再复用旧的 5% 历史回归口径。

3. 哪些看似放大，但现在不能局部删除

1 MiB 写当前必须保持 1 次 write + 1 次 commit。 这是现行 RPC 放大合同；未来如果内核、FUSE provider 或写路径调整导致 1 MiB 再次被拆成多个前台 commit，放大门禁会失败。 DMS 仍采用 write-through：write 返回时版本已经发布；这不等于启用 writeback。
TTL=0 与 DIRECT_IO 暂时保留。 Node 已通过 watch 撤销自己的 binding/cache，但尚未把失效事件闭环到内核 FUSE cache。 在具备 notifier 前启用较长 entry/attr/page cache 会改变跨客户端可见性，不是安全优化。
readdir 权威分页已收口。 Meta 使用 BTreeMap(parent,name) 从 cursor 起只返回一页；Node 以 (directory,cursor) 为键缓存页；FUSE handle 仅保存 cookie→cursor，不收集或排序完整目录。 300 个目录项的单 VM/三 VM 用例已跨越 256 项单页上限。

4. max_pages 类问题的最终结论

fuser 0.16 + abi-7-31 已默认协商 ASYNC_READ、BIG_WRITES，并在内核支持时请求 MAX_PAGES；默认接收缓冲允许 16 MiB。当前不缺另一个手写的 max_pages 开关。

真正应长期保留的是“实测分段账本”：例如 1 MiB peer 首读可以被内核拆成多个 FUSE read callback，但 DataCore 读取总字节必须等于 1 MiB，Peer PullBlock 必须保持 1 次；如果未来变成多个 PullBlock 或多个前台 commit，机器合同会直接失败。
