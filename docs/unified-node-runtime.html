DMS Unified Node Runtime 穿刺代码导读

本文面向代码 review：解释为什么要把文件系统和镜像懒加载入口放进 dms-node，以及当前候选代码如何保证它们复用既有 Node 数据路径， 而不是绕一圈调用 KV SDK 或本地 Worker RPC。

1. 目标与边界

本轮要证明什么

目标 文件系统入口、镜像懒加载入口可以进入 dms-node 进程内， 直接调用统一对象核心，复用 Node 已有的版本、range、Arena、Peer、Meta、缓存和观测能力。

本轮不改变什么

边界 KV SDK、Worker protobuf、Client/Node/Meta 进程边界、MetaState/NodeState owner 模型不变。 现有 KV 能力继续保留。

为什么不是再做一个服务

原则 如果文件系统或镜像入口再通过本地 SDK 调 Worker RPC，就会把“进程内能力”退化成“本机远程调用”， 性能和抽象都会变差。

本轮增加两个彼此独立的进程内子系统入口：

  • FileOperations：文件子系统自己的语义层，把 path、offset、write/read/delete 转换成对象 key 与 byte range。
  • ImageReader：镜像子系统自己的懒加载入口，打开对象时固定版本，后续按固定版本读取 range。

真正的 Linux FUSE callback 在 server/src/node/filesystem/fuse.rs。 它只负责接内核请求并调用 FileOperations，不包含独立对象存储逻辑。 这里不再定义一个 KV/文件/镜像共用的上层入口类型或 trait；三者真正共用的是 NodeHandle → NodeState，进程内子系统额外共用 DataCoreHandle。

2. As-Is / To-Be

维度 As-Is：外部文件系统适配器路径 To-Be：统一 Node Runtime 穿刺路径
文件读写入口 内核 FUSE → 外部进程 → 对象后端适配器 → DMS SDK → 本地 Node Worker 内核 FUSE → dms-node 内置 FUSE → FileOperations → DataCoreHandle
是否走 KV SDK 走 SDK；SDK 负责连接本地 Node 不走 SDK；入口已经在 Node 进程内
是否走 Worker RPC 至少有一次本地 Worker RPC 进程内子系统必须为 0 次 Worker RPC
状态 owner NodeState 仍是唯一 owner，但入口在进程外 仍是同一个 NodeState owner；DataCore 只是 mailbox 入口
性能观测 需要区分外部适配器、SDK、Worker RPC、Node 内部开销 重点看 DataCore → Meta / Peer / Arena / cache 的账本

2.1 新目标下的目录设计

目录按“谁拥有语义”组织，不按笼统的入口类型组织。当前已经实现的文件直接落盘；尚未实现的镜像设备、 Overlay 挂载等只有在出现第二个真实文件时才拆子目录，不提前创建空壳。 

source/
├── sdk/                              # 外部 KV SDK；Rust/Go 等语言合同保持不变
├── protocol/                         # 只放跨进程 wire 合同
├── common/                           # transport / shm / errors / logs / metrics / tracing
└── server/
    └── src/
        ├── node.rs                   # dms-node 组合根：装配 listener、Meta、Node owner、可选 FUSE
        ├── meta.rs                   # dms-meta 组合根
        └── node/
            ├── runtime.rs            # NodeHandle + 唯一 NodeState owner
            ├── worker_service.rs     # 外部 KV RPC 适配；直接调用 NodeHandle
            ├── data_core.rs          # 进程内 Object/Version/Range API；只包装 NodeHandle
            ├── filesystem/
            │   ├── mod.rs            # 文件 path/offset/truncate 等文件语义
            │   └── fuse.rs           # Linux FUSE callback 与 inode/fh 临时状态
            ├── image/
            │   └── mod.rs            # 镜像固定版本、range lazy-read 语义
            ├── arena_manager.rs      # Region/Allocation/Block 物理内存
            ├── current_cache.rs      # Node Current layout cache
            ├── version_layout.rs     # Version/Extent 布局算法
            ├── metadata_client.rs    # Node → Meta
            ├── peer_service.rs       # Node ↔ Node
            └── ...                   # metrics、reporter、KKV 等已存在模块

后续只有真实实现到来时才按下面规则扩展：

# 出现镜像设备接入后，在现有 image 领域目录中增加真实接入：
node/image/
├── mod.rs                            # ImageReader 与镜像层语义
└── <实际设备接入>.rs                 # 例如块设备/懒加载 callback；名称按所选技术确定

# 出现 Overlay 快照接入后，独立建立：
node/overlay/
├── mod.rs                            # snapshot/layer/mount 的领域语义
└── <实际内核接入>.rs                 # 只放真实接入代码，不建立公共入口壳

收敛点：WorkerService 与 DataCoreHandle 是两个并列边界； WorkerService 表达远端 session/staging/wire，DataCoreHandle 表达进程内 object/version/range。 二者都进入同一个 NodeHandle，因此没有第二份状态。

3. DataCore：不是第二个 runtime

DataCoreHandle 的名字容易误解。当前实现里它不拥有对象 map、版本表、Arena 或 Peer 连接， 也不启动新的 actor。它只保存一个 NodeHandle，然后把进程内入口的对象操作转换成已有 NodeCommand。 

外部 KV：应用 → SDK → WorkerService ───────────────┐
                                                    │
进程内文件：FUSE → FileOperations → DataCoreHandle ├─→ NodeHandle mailbox
                                                    │
进程内镜像：ImageReader ─────────→ DataCoreHandle ─┘
        │
        ▼
唯一 NodeState owner
        ├─ Current layout cache
        ├─ Arena / Region / Block
        ├─ Peer pull singleflight
        ├─ Meta resolve / commit / report
        └─ metrics / trace / log

这条边界带来两个 review 判断：

  • 应该保留：DataCoreHandle 作为文件、镜像等进程内子系统的对象合同。
  • 应该直接：WorkerService 保留 session/staging/wire 语义并直接调用 NodeHandle。
  • 不应该出现：DataCore 内部新建 MetaState、NodeState、SDK client、tonic service、FUSE inode 或镜像 blob 结构。
  • 不应该出现：DataCore 携带 Worker session，或为了形式统一再增加一层公共入口。

3.1 DataCore 的最小语义

抽象 意义 代码位置
ObjectKey 对象稳定名字。文件入口会把 path 转为 fs:<path>；镜像入口直接使用对象 key。 server/src/node/data_core.rs
ByteRange 对象某个版本内的一段逻辑字节。 server/src/node/data_core.rs
VersionSelector Current 读最新可见版本；Exact 读打开时固定的版本。 server/src/node/data_core.rs
read_into 表达“调用方给目标 buffer”的合同。当前 mailbox 边界仍有一次内部 Vec 转交，后续可继续优化。 server/src/node/data_core.rs
write_range 表达随机写：只提交 patch Block 和 Extent overlay，不把整个对象读出再重写。 server/src/node/runtime.rs

4. KV / FUSE / Image 三入口时序

4.1 KV get_range：外部 SDK 继续走 Worker 边界

应用进程
  │  dms-client get_range(key, offset, len)
  ▼
本地 WorkerService
  │  protobuf 请求；保持既有外部合同不变
  ▼
NodeHandle / NodeState
  │  Current cache 命中：直接 Arena 读
  │  miss：Meta resolve → 如缺 Block，则 Peer pull → Arena 安装 → 回填 Current cache
  ▼
返回 bytes 或 SHM 描述

KV SDK 是对外合同，所以本轮不把它改成进程内 DataCore API。它可以复用同一 NodeState 内部能力，但仍保留 Worker RPC 边界。

4.2 FUSE create/write/read/delete：内核请求进入 Node 进程内

Linux kernel FUSE
  │  create("/a") / write("/a", off, bytes) / flush / read("/a", off, len) / unlink("/a")
  ▼
server/src/node/filesystem/fuse.rs
  │  同步 callback；用现有 Tokio Handle 调 async 文件操作
  │  新文件的多个 write callback 按 inode 聚合；多个 handle 共享一份 pending bytes
  │  flush/release 把 Vec 所有权一次性交给 DataCore
  ▼
FileOperations
  │  path → ObjectKey("fs:/a")
  │  create_with_contents：新文件及首批 bytes 一次条件提交
  │  write 扩容：文件层补零/构造新 value
  │  write_range：保持为对象 range patch
  ▼
DataCoreHandle
  ▼
NodeState / Arena / Meta / Peer

当前 FUSE 命名空间是穿刺版本：只支持根目录下一层普通文件，inode/dentry 不持久化到 Meta。 已知 path 在另一 Node 首次 lookup 时会通过 DataCore 查询对象并建立本地 inode，随后读取进入 Meta resolve → Peer pull → Arena 安装；readdir 仍只展示本进程已经发现的名字。 对象内容、版本、range overlay 和跨节点拉取全部进入 DMS core。

4.3 Image lazy range：打开时固定版本，读时按 range 懒加载

ImageReader.open_layer(object)
  │  stat(object) → 固定 version + length
  ▼
ImageLayer { key, version, length }

ImageReader.read_exact_at(layer, offset, buffer)
  │  VersionSelector::Exact(layer.version)
  ▼
DataCoreHandle.read_into(...)
  │  本地已有 Block：Arena 读入目标 buffer
  │  本地缺 Block：Peer pull 一次，安装到本 Node，再读
  ▼
第二次读同一 range：不应再产生 Peer payload

镜像入口的关键语义是“固定版本”。这样上层读多个 range 时，不会因为 Current 变化而读到混合版本。 当前第二次读取同一 Exact range 仍会向 Meta 解析该固定版本布局，但不会再次产生 Peer payload； “Exact layout cache 命中后 Meta 也为 0”是后续优化目标，不把它写成当前已经实现。

5. 真实 FUSE 配置与单 VM 手动步骤

FUSE 支持只在 Linux 且启用 fuse feature 时编译。默认构建不启用该 feature， 因而不会影响普通 KV 二进制依赖和启动路径。

5.1 配置入口

入口 字段 说明
命令行 --fuse-mountpoint <dir> 只在 fuse feature 下存在；不传则不启动 FUSE。
配置文件 fuse_mountpoint 由 ResolvedNodeConfig 合并；命令行优先级更高。
源码开关 dms-server/fuse 引入 fuser 和 libc 可选依赖。

5.2 单 VM 手动验证

以下流程已在 Linux VM 中实测。VM 需要具备 /dev/fuse 和 fusermount3；先在 VM 中进入已同步的源码目录，再分终端执行下面的短命令。 

# 终端 1：进入源码目录并准备挂载点
cd /path/to/rust-distributed-memory-store/source
mkdir -p /tmp/dms-fuse-mnt

# 终端 2：启动 Meta
cargo run -p dms-server --bin dms-meta -- serve \
  --node-id meta-1 \
  --grpc-address 127.0.0.1:25300 \
  --health-address 127.0.0.1:25301 \
  --journal-dir /tmp/dms-meta-journal

# 终端 3：启动带 FUSE 支持的 Node
cargo run -p dms-server --features fuse --bin dms-node -- serve \
  --node-id node-a \
  --meta-endpoint http://127.0.0.1:25300 \
  --worker-tcp-address 127.0.0.1:25400 \
  --health-address 127.0.0.1:25401 \
  --fuse-mountpoint /tmp/dms-fuse-mnt

# 终端 4：通过挂载目录验证 create / read / random write / delete
printf 'abcdef' > /tmp/dms-fuse-mnt/a
cat /tmp/dms-fuse-mnt/a
printf 'ZZ' | dd of=/tmp/dms-fuse-mnt/a bs=1 seek=2 conv=notrunc
cat /tmp/dms-fuse-mnt/a
truncate -s 3 /tmp/dms-fuse-mnt/a
cat /tmp/dms-fuse-mnt/a
rm /tmp/dms-fuse-mnt/a
ls -la /tmp/dms-fuse-mnt

# 清理：先卸载，再停止 Node/Meta
fusermount3 -u /tmp/dms-fuse-mnt

6. RPC 与复制账本

本轮不允许只用端到端耗时讲性能。每个候选 Case 必须同时给出路径账本，证明慢在哪里： 是入口层多绕 Worker RPC，还是 Meta 解析多，还是 Peer payload 多，还是复制/分配多。

字段 含义 目标判断
entry_worker_rpc 衡量文件/镜像进程内入口是否绕回 Worker RPC。 FS/Image 必须是 0。
node_meta_resolve Node 为读取 key/version 向 Meta 查询位置的次数。 首读允许；Node 热读应由 Current cache 降低。
node_meta_commit 写入、range patch、delete 发布新版本的次数。 有版本变化时不可省。
node_meta_report Node 后台向 Meta 报告本地已有副本的次数。 不应进入用户前台等待路径。
node_peer_pull_count / node_peer_pull_bytes 本 Node 缺 Block 时从 owner Node 拉取的次数和字节数。 首读允许；第二次相同 range 必须为 0 字节。
current_cache_hit / current_cache_miss Node Current layout cache 的命中情况。 本节点热读和跨节点接管后的热读应逐步命中。
payload_full_copy 完整 payload 被额外拷贝的次数。 大对象路径应避免不必要的整对象复制。
payload_allocation payload 层显式分配 buffer/slot 的次数。 热读不应产生额外 payload allocation。

8. 真实端到端证据

本次使用同一组 12 文件 workload，对比“外部文件系统进程 + SDK + Worker”与 “dms-node 内置 FUSE + DataCore”。两条路径都经过真实内核 FUSE， 且都覆盖单节点与双 Node 跨节点首读，因此不再用 SDK 微基准代替端到端结论。

单 VM 复现入口：scripts/performance/run_unified_node_runtime_workload.sh，用于验证内置 FUSE/DataCore 的结构路径与单机工作负载，不宣称单独复现完整双 Node 对照。

完整实验结果摘要：benchmarks/whitebox/results/unified-node-runtime-20260913.json，记录此前完成的单节点、双 Node 与外部适配器对照，并保存原始证据哈希。

合同与评价器：benchmarks/whitebox/contract.json 与 scripts/performance/evaluate_whitebox.py

判定：12 项性能门禁全部通过。

产品源码仓只保留单 VM 可复现入口、机器可读的完整实验摘要与原始证据哈希；大量原始日志、metrics 和逐轮样本不进入源码发布件。

9. 约束、未完成边界与 review 重点

9.1 当前已经固化的约束

  • 只有一个 NodeState owner；DataCore 不保存第二份对象状态。
  • 只有一个 MetaState owner；文件和镜像语义不进入 Meta 内部结构。
  • 默认 KV 构建不包含 FUSE 依赖；FUSE 只在 Linux feature 下启用。
  • 文件/Image 进程内子系统不能依赖 dms-client、dms-protocol 或 tonic。
  • Image lazy read 打开后读固定版本；Current 变化不影响已打开 layer。

9.2 当前仍需后续收口的点

事项 现状 下一步判断
真实 FUSE e2e 测量 已完成单节点和双 Node 外部适配器对照，12 项门禁全部通过。 后续回归直接复用当前 workload 与 candidate schema。
read_into 的最终零拷贝 DataCore 合同接受调用方 buffer；当前 mailbox 边界仍使用内部 Vec 转交。 若证明该复制成为瓶颈，再设计安全的借用/共享目标 buffer 机制。
Exact version layout cache Current cache 已复用；固定版本读目前主要保证 Peer payload 不重复。 镜像场景若 Meta resolve 成为瓶颈，再加入固定版本 layout cache。
FUSE 命名空间持久化 穿刺版本的 inode/dentry 仍是进程内状态；已知 path 可在另一 Node 懒发现并首读，readdir 只列出本地已发现项。 产品化阶段设计目录元数据、恢复与跨 Node 命名空间事件。
新文件可见性边界 create 先在本进程命名空间可见；同 inode 的多个 handle 共享 pending bytes，flush/release 做一次 put_if_absent；首次提交前 unlink 只清理本地 pending 状态。 这是穿刺版的 dirty-handle 事务边界；持久命名空间完成后再统一 create 冲突时机。
并发与容量安全 扩容写和 truncate 使用版本 CAS；read_into 在读取容量变化时重试；重复 create 返回 EEXIST。 保持回归测试，不向 DataCore 增加文件系统专用状态。
Image 真正内核入口 当前是语义壳和 lazy range 读穿刺。 后续根据实际镜像挂载方式补充设备/daemon 层。

9.3 Review 时优先看的问题

  1. DataCoreHandle 是否真的只是 NodeHandle 薄入口，没有引入第二份状态。
  2. WorkerService 与 DataCoreHandle 是否保持并列，DataCore 中没有 session/staging。
  3. FUSE callback 是否只在 filesystem/fuse.rs，没有把 inode/dentry 泄漏到 DataCore。
  4. 文件中段覆盖是否生成 Extent overlay，而不是整对象读出再写回。
  5. Image 第二次相同 range 是否不再产生 Peer payload。
  6. 新增 feature 是否不影响默认 KV 构建。

本文描述已通过 Linux 真实 FUSE、双 Node 首读与完整外部适配器对照的穿刺实现。产品化命名空间和镜像内核入口仍是明确后续项。
