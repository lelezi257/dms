# 按阶段交付 DMS

先读源码根 `AGENTS.md` 和用户当前请求，再查 `docs/product.md`、目标模块代码及本次已有计划；不要加载全部历史设计。这里所有相对源码路径都以包含 `sdk/`、`server/` 的源码根为基准。

## 1. 确定当前阶段，只读对应模板

| 阶段 | 必读模板 | 人工只需要判断 |
| --- | --- | --- |
| 需求 | [requirements.md](references/requirements.md) | 要解决什么、做与不做、怎么验收 |
| 设计 | [design.md](references/design.md) | 进程和模块边界、核心原理、接口是否支撑用户用例 |
| 穿刺 | [spike.md](references/spike.md) | 先判断实验能否回答问题，再判断结果是否足够 |
| 实现 | [implementation.md](references/implementation.md) | 代码批次是否可理解，真实行为是否符合已确认设计 |
| 验收/发布准备 | [verification.md](references/verification.md) | 证据是否足够、限制是否明确、是否允许下一阶段 |

用户已经批准的工作，继续完成该阶段，不为每个文件再问一次。用户只要求讨论时不要修改代码。跨阶段 review 门禁以本次计划为准；未获授权不要进入发布或扩大产品范围。

## 2. 先短后深

开始时用几句话写本轮目标、边界、产物位置、成功条件；模板只填写与本轮相关的项。小修可以直接在同一变更说明中保留“问题—改法—验证—风险”，不生成额外 review.md。

设计先从真实 `set/get/del/set_range/hset` 输入说明原理，再介绍模块、状态及函数；代码位置最后用于反查。定义新抽象时必须给出调用者、被调用者、状态 owner 与一个实际用例；不能说明价值就先复用现有实现。

基础组件约定直接引用 `docs/contributing.md`，不要为日志、metrics、trace、错误或配置另起一套框架。实现前读取目标模块及其 tests，确认现有入口仍有效。

## 3. 环境与证据不后补

涉及命令时先区分宿主启动 VM 与 VM 内实际执行，沿 `docs/local-single-vm-manual.md` 使用已确认环境。编译、测试、文档生成与性能执行都在 Linux；不能为了省事换成 Mac 运行。隔离端口、目录和进程，禁止清理别人的 journal。

在修改前定验收项；改后记录命令、实际结果、原始证据位置和未测项。进程 ready 不等于 bytes 正确；接口骨架/mock 不能宣称真实 E2E。失败证据不覆盖。

阶段审阅文档按相邻 `dms-review-artifact/SKILL.md` 输出。若工作区有独立状态文件，更新唯一当前入口和下一动作；源码独立 checkout 时使用本次约定的跟踪文档，不依赖仓外路径。

## 4. 交付时停止在约定边界

报告结果、关键入口、证据和最多几个需要人决定的问题。涉及缓存/SHM/WAL 等风险，区分本轮修复与完整 GC/HA 等未完成能力。不要因为测试绿就声称可生产或已发布。
