3. 三条代表路径

3.1 同节点热读：架构优势已经兑现

应用 read→Linux VFS/FUSE→进程内文件入口→Node 本地 Block

前台 0 次 Worker RPC、0 次 Meta、0 次 Peer。一个数据段只有一次必要的“Node bytes → FUSE 回复缓冲”复制。4 KiB p50 为 586 µs，其中约 214 µs 在 Node 文件 handler；剩余约 34% 已明确归入 syscall、VFS/FUSE 调度和 workload 包装边界，而非未知 DMS 成本。

3.2 跨节点首次接管：只保留分布式系统必需阶段

B 上应用 read→B 查一次 Meta→B 向 A Pull Block→B 写本地 Arena

4 KiB、64 KiB 和 1 MiB 当前均为 1 次 Lookup + 1 次 PullBlock。1 MiB 会被内核拆成多个 FUSE read callback，但 Peer 数据拉取仍只有一次；后续热读不再访问 Meta 或 Peer。

3.3 中段覆盖：只写 patch，不重写整文件

pwrite 4 KiB→新建 patch Block→复用前后 Extent→一次 Meta 原子发布

旧文件 bytes 不再先读回并拼成完整新文件。新版本由“旧前缀 Extent + patch Extent + 旧后缀 Extent”组成；Node 只持久化本次 patch，Meta 仍只有一个版本发布点。

3.4 新建并写入：三次控制动作不是重复 RPC

negative lookup→create 空 inode→write-through commit

open(O_EXCL) 先由内核确认名字不存在；FUSE create 发布一个可见的空文件；随后独立的 write callback 才提交内容。没有 writeback 时，不能把 create 和 commit 合并后提前返回。该成本基本不随 payload 增长，因此 release 使用绝对微秒预算，而不是让相同的固定成本在 4 KiB/64 KiB 上被百分比放大。

4. 本轮代码为什么会更快

修改旧路径新路径收益
文件扩容 Extent overlay追加/越过 EOF 时可能读回旧对象并完整重写只新增 tail/patch Block，复用旧 Extent避免与文件大小成比例的读回和复制
FUSE ABI 7.31Linux 曾把 1 MiB 写拆成多个 callback协商 max_pages，当前门禁要求 1 MiB 单 write callback守住单 commit 写入路径
文件 I/O bytes 指标只能看到 callback 次数同时看到 read/write bytes可区分“请求多”与“请求被拆小”
路径机器合同只看端到端数字RPC、Peer、拷贝阶段均需匹配防止性能数字掩盖语义缺失
拷贝口径：payload_copy_stages 是单个数据段的完整字节复制路径深度，不是一个文件操作内所有分段复制次数之和。1 MiB 写当前由实测 write/commit 次数守住单段路径；Peer 首读由 PullBlock 次数守住跨节点数据路径。

5. 仍然存在但本轮不应继续“优化”的边界

write-through 不是 writeback。当前 1 MiB 已是单 write / 单 commit；write 返回时版本已经发布。后续若要进一步优化小写或覆盖写，只能在保持同步发布语义下减少固定控制开销，不能引入后台脏页来改变成功返回含义。

首次文件内容提交当前会向全部 active Node 发 binding invalidation，即使某些 Node 从未缓存该 inode。未来可用 grant-holder 精确投递，但会增加可恢复状态；当前 memory-mode 结果已通过，不作为本轮 blocker。

6. 持久化对比为什么单列

补充实验曾把 DMS Meta 的 local WAL 与无持久化 Glue 元数据直接比较。读取仍领先，但小写和覆盖出现落后；这不是 Native 路径退化，而是可靠性合同不相等。公平的下一阶段应比较“DMS local WAL”与“对照端每次写同步落盘”，不能把该组数字并入本基线。
