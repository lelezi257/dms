DMS M1 共享 Namespace E2E 验证导读

这份导读对应 M1 的第一条目录树验收线：不通过 SDK 或内部函数作弊，只通过两个 FUSE mount 做普通 POSIX 操作，验证 Meta 是共享 namespace 的唯一权威，Node 只是 缓存授权结果。

1. 这条 E2E 代表什么

用户动作必须证明的系统能力为什么足够代表 M1 骨架
A 执行 mkdir project/src/pkg 目录 inode、dentry、目录 revision 由 Meta 原子发布 覆盖多级 path 解析，不再是根目录临时 HashMap
A 创建并写入 module.txt，B 读取 namespace 的 path→inode 和 DataCore 的 inode→内容版本能串起来 证明文件系统层没有复制第二套 Extent/Block
A rename，B 旧名消失、新名可读 目录 mutation、目录缓存失效、内容 binding 不随名字移动而改变 覆盖最容易暴露“双 Current”或局部缓存错误的路径
尝试把目录移入自身子树，以及文件/目录交叉覆盖 拒绝 namespace 环并执行 POSIX rename 类型矩阵 证明错误请求会在写 journal 之前失败，不会留下不可回放状态
A unlink + rmdir 普通文件名字删除、非空目录保护、空目录删除 覆盖 POSIX 目录基础约束；unlink-open 最终回收仍是后续阶段
Meta 与 B 重启后再读锚点文件 journal/checkpoint/replay 恢复 namespace 与文件绑定 证明不是只靠进程内缓存通过

2. 新增文件

文件用途Review 重点
scripts/validation/run_filesystem_namespace_e2e.sh 启动 Meta、两个 Node、两个 FUSE mount，运行 20 轮 namespace E2E 和重启恢复 端口、清理、重启顺序是否和既有 shared-file E2E 一致
scripts/validation/run_filesystem_namespace_3vm.py 把 Node A、Node B、Meta 分别部署到三台 Lima VM，执行同一份 20 轮合同 私网地址、精确 PID 清理、二进制 SHA256 和跨机 Peer payload 是否真实
scripts/validation/filesystem_namespace_workload.py 纯 POSIX workload：mkdir/create/read/rename/类型与环保护/unlink/rmdir/recovery 是否只表达用户语义，没有调用 DMS 内部 API
scripts/validation/evaluate_filesystem_namespace.py 机器判定：检查轮次、每轮操作、恢复文件和基础 metrics 失败时是否能给出明确缺口，不虚构通过
benchmarks/whitebox/filesystem-namespace-contract.json M1 namespace 验收合同 required / non-goal 是否和阶段边界一致

3. 如何手动运行

必须在 Linux 且有 /dev/fuse 的 VM 内运行。macOS 主机只用于阅读和编辑。 

cd /path/to/dms/source
DMS_FILESYSTEM_NAMESPACE_ROUNDS=20 \
  scripts/validation/run_filesystem_namespace_e2e.sh

3.1 三 VM 手动验证

先在 Linux 构建机生成带 FUSE 的两个二进制，并复制到 macOS 控制机：

cargo build -p dms-server --bins --features fuse

python3 scripts/validation/run_filesystem_namespace_3vm.py \
  --dms-node /path/to/linux/dms-node \
  --dms-meta /path/to/linux/dms-meta \
  --output evidence/2026-09-15-filesystem-namespace/three-vm-reviewed-final \
  --vm-a g003-n1 --ip-a 192.168.104.8 \
  --vm-b g003-n2 --ip-b 192.168.104.9 \
  --vm-c g003-n3 --ip-c 192.168.104.10 \
  --rounds 20

控制器把 A/B/C 固定为写入 Node、观察 Node、Meta；只管理本次 run directory 和记录过的 PID，不按进程名杀服务。三台 VM 都需要私网互通，A/B 需要 /dev/fuse 和 fusermount3。

脚本成功时会打印证据目录，并生成：

namespace-workload.json
namespace-recovery.json
evaluation.json
node-a.prom
node-b.prom
meta.prom
meta.log / node-a.log / node-b.log / restarted logs
result.txt

4. 当前验收结果

2026-09-15 的单 VM 双 Node 和三 VM 分布式结果均为 PASS：每组 20 轮，每轮均覆盖 mkdir/create/read/readdir/rename/unlink/rmdir，以及 rename 的目录环、 文件覆盖目录、目录覆盖文件三类拒绝路径；随后重启 Meta 与 Node B，最后一轮锚点文件仍可按原路径读取。

机器证据位于 evidence/2026-09-15-filesystem-namespace/，其中 three-vm-reviewed-final/profile.json 固定部署角色和二进制 SHA256。验证过程中修复了 Meta DirectoryNotEmpty 在 FUSE 边界被降级为 EIO、目录可移入自身子树， 以及 rename 缺少文件/目录替换矩阵三类问题；现在用户可得到稳定的 ENOTEMPTY/EINVAL/EISDIR/ENOTDIR。

5. 后续实现需要对齐的代码入口

层次入口需要满足的合同
FUSE server/src/node/filesystem/fuse.rs callback 只做参数翻译，不能拥有权威目录树
Node 文件入口 server/src/node/filesystem/shared.rs 提供 mkdir/readdir/rename/unlink/rmdir 的进程内方法，继续复用 NodeHandle/DataCore
Node→Meta 客户端 server/src/node/filesystem/meta_client.rs 只做领域类型到 protobuf 的转换，不缓存 namespace 状态
Meta 权威状态 server/src/meta/filesystem/mod.rs 所有 namespace mutation 在 Meta owner 内完成 CAS、revision、idempotency
Meta journal server/src/meta/metadata_journal.rs / local_wal_journal.rs 一次 mutation 对 inode/dentry/directory revision 的影响必须可 replay
Watch 失效 protocol/proto/dms/v1/node_meta.proto 与 server/src/node.rs 目录级 revoke 先删除 Node dentry/readdir cache，再 ACK
